===================================================================================
                    GOVGRANT AI — COMPLETE WORKING PROCEDURE
================================================================================

Project: AI-powered grant discovery platform for Indian businesses
Stack:   Next.js 16 (frontend) + FastAPI (backend) + Google ADK + Gemini 2.0 Flash
DB:      SQLite via SQLModel | Vector Store: ChromaDB | Embeddings: text-embedding-004

================================================================================
1. HIGH-LEVEL ARCHITECTURE
================================================================================

    User Browser (localhost:3000)
         |
         |  HTTP / SSE
         v
    Next.js 16 Frontend (TypeScript, Tailwind CSS)
         |
         |  REST API calls
         v
    FastAPI Backend (localhost:8000)
         |
         ├── /api/auth/register   — User registration
         ├── /api/auth/login      — JWT login
         ├── /api/sessions        — Create session
         ├── /api/chat            — Conversational intake (Agent 1)
         ├── /api/pipeline        — SSE streaming pipeline (Agents 2→3→4)
         ├── /api/results/{id}    — Fetch final report
         ├── /api/alerts          — Schedule deadline alerts
         └── /api/history         — Past sessions list
         |
         v
    4-Agent Sequential Pipeline (Google ADK)
         |
         ├── Agent 1: IntakeAgent      → writes user_profiles table
         ├── Agent 2: ResearchAgent    → writes raw_schemes table
         ├── Agent 3: ValidatorAgent   → writes ranked_schemes table
         └── Agent 4: PlannerAgent     → writes grant_reports table
         |
         v
    SQLite Database (govgrant.db) — 7 tables
    ChromaDB Vector Store (data/chroma_db/) — indexed scheme PDFs


================================================================================
2. DATABASE SCHEMA — 7 TABLES
================================================================================

Table 1: users
    id              TEXT PRIMARY KEY (UUID)
    email           TEXT UNIQUE
    name            TEXT
    hashed_password TEXT
    created_at      DATETIME

Table 2: sessions
    session_id      TEXT PRIMARY KEY (UUID)
    user_id         TEXT FK→users.id
    user_email      TEXT (for alert delivery)
    created_at      DATETIME
    status          TEXT (intake | researching | validating | done)

Table 3: user_profiles (owned by Agent 1)
    id              INTEGER PRIMARY KEY
    session_id      TEXT FK→sessions.session_id
    name            TEXT (business name)
    type            TEXT (startup | msme | proprietorship | private_limited | ...)
    sector          TEXT (food_processing | it_tech | agriculture | ...)
    state           TEXT (Maharashtra | Karnataka | ...)
    city            TEXT
    team_size       INTEGER
    revenue_inr     INTEGER
    funding_purpose TEXT
    created_at      DATETIME

Table 4: raw_schemes (owned by Agent 2)
    id              INTEGER PRIMARY KEY
    session_id      TEXT FK→sessions.session_id
    scheme_name     TEXT
    source_url      TEXT
    source_type     TEXT (live | offline)
    criteria_text   TEXT
    deadline        DATE (nullable)
    max_revenue_inr INTEGER (nullable)
    eligible_types  TEXT (JSON array as string)
    created_at      DATETIME

Table 5: ranked_schemes (owned by Agent 3)
    id              INTEGER PRIMARY KEY
    session_id      TEXT FK→sessions.session_id
    scheme_name     TEXT
    match_score     INTEGER (0-100)
    rank            INTEGER (1-5)
    reason          TEXT
    urgency_score   FLOAT (0.0-1.0)
    composite_rank  INTEGER
    portal_url      TEXT
    deadline        TEXT
    grant_amount    TEXT
    created_at      DATETIME

Table 6: grant_reports (owned by Agent 4)
    id              INTEGER PRIMARY KEY
    session_id      TEXT FK→sessions.session_id (UNIQUE)
    documents_json  TEXT (JSON array as string)
    action_cards_json TEXT (JSON array as string)
    cover_summary   TEXT
    created_at      DATETIME

Table 7: alerts (owned by Agent 4)
    id              INTEGER PRIMARY KEY
    session_id      TEXT FK→sessions.session_id
    user_email      TEXT
    scheme_name     TEXT
    deadline        DATE
    alert_type      TEXT (email_T-14 | email_T-3 | whatsapp_T-14 | whatsapp_T-3)
    status          TEXT (pending | sent | failed)
    sent_at         DATETIME (nullable)
    created_at      DATETIME


================================================================================
3. SESSION ID — THE GLUE
================================================================================

Every user session has a session_id (UUID) generated by the frontend the
moment the user opens /chat. This ID travels through:

    Frontend localStorage → API calls → Every agent → Every DB table

Rule: NEVER generate a new session_id mid-session. One session = one UUID
from start to finish.


================================================================================
4. COMPLETE USER FLOW (Step by Step)
================================================================================

STEP 1: User opens http://localhost:3000
    → Landing page renders with "Get Started" button
    → Beautiful hero section with stats and feature cards

STEP 2: User clicks "Get Started"
    → Redirects to /register (if new) or /login (if returning)
    → User enters name, email, password
    → Backend creates User row, returns JWT token
    → Token stored in localStorage

STEP 3: User arrives at /chat
    → Frontend calls POST /api/sessions
    → Backend creates ChatSession row (status: "intake")
    → session_id stored in localStorage
    → Chat UI renders with bot greeting

STEP 4: Conversational Intake (Agent 1)
    → User answers 6 questions via chat:
      Q1: Business name → "GreenLeaf Organics"
      Q2: Entity type   → "Private Limited"
      Q3: Sector        → "Food Processing"
      Q4: State & City  → "Maharashtra, Pune"
      Q5: Team size     → "12 employees"
      Q6: Revenue & Purpose → "80 lakhs, technology upgrade"
    → Each message hits POST /api/chat
    → Backend uses Gemini 2.0 Flash (or fallback questions)
    → Progress bar updates as fields are collected
    → On 6th answer: profile persisted to user_profiles table
    → Session status → "researching"
    → Frontend auto-redirects to /processing

STEP 5: Processing Page — SSE Pipeline
    → Frontend calls POST /api/pipeline
    → Backend streams 4 SSE events in sequence:

    EVENT 1: intake_done
        → Reads profile from user_profiles table
        → Emits profile JSON as SSE payload
        → Processing page: Intake Agent card turns GREEN ✓

    EVENT 2: research_done (Agent 2)
        → ResearchAgent runs:
          a) ChromaDB RAG query (pre-indexed scheme PDFs)
          b) Gemini Google Search grounding (live web results)
          c) Merge + deduplicate → 15-25 raw schemes
        → Persists to raw_schemes table
        → Emits scheme array as SSE payload
        → Processing page: Research Agent card turns GREEN ✓

    EVENT 3: validation_done (Agent 3)
        → ValidatorAgent runs:
          a) Hard filter: revenue cap, entity type, state check
          b) Gemini LLM scoring on 4 dimensions:
             - Eligibility (0-40)
             - Relevance (0-30)
             - Benefit (0-20)
             - Ease (0-10)
          c) Rank top 5 by composite score
        → Persists to ranked_schemes table
        → Session status → "validating"
        → Emits ranked array as SSE payload
        → Processing page: Validator Agent card turns GREEN ✓

    EVENT 4: report_ready (Agent 4)
        → PlannerAgent runs:
          a) Reads ranked_schemes from DB
          b) Gemini generates:
             - Documents checklist (10-15 items, deduped)
             - Action cards (1 per scheme, with steps + tips)
             - Cover summary (150 words, first person)
          c) Falls back to curated report if Gemini fails
        → Persists to grant_reports table
        → Session status → "done"
        → Emits full report as SSE payload
        → Processing page: Planner Agent card turns GREEN ✓

    → After report_ready: auto-redirect to /results/{session_id}

STEP 6: Results Page
    → Frontend calls GET /api/results/{session_id}
    → Backend reads from ranked_schemes + grant_reports tables
    → Page renders:
      LEFT COLUMN:
        - 5 GrantCard components (scheme name, score badge, reason, apply link)
      RIGHT COLUMN:
        - Checklist component (10-15 required documents)
        - Action Cards (per-scheme steps with estimated days)
        - CoverSummary component (150 words, copy-to-clipboard button)
    → "PDF Report" button triggers browser print
    → "Set Alerts" button navigates to /alerts

STEP 7: Alerts Page
    → User enters notification email
    → Optional: enable WhatsApp alerts with phone number
    → Frontend calls POST /api/alerts
    → Backend creates Alert rows:
      - email_T-14: email alert 14 days before each deadline
      - email_T-3: email alert 3 days before each deadline
      - whatsapp_T-14 / whatsapp_T-3 (if WhatsApp enabled)
    → Success animation → redirect back to results

STEP 8: History Page (/history)
    → Frontend calls GET /api/history
    → Lists all past sessions with:
      - Business name, sector
      - Status badge (Intake / Researching / Validating / Complete)
      - Click to view completed reports


================================================================================
5. AGENT DETAILS
================================================================================

─── AGENT 1: IntakeAgent (intake_agent.py) ─────────────────────────────────

  Purpose:    Collect 6 business profile fields via natural conversation
  Model:      Gemini 2.0 Flash (temperature: 0.3)
  Tools:      finalize_profile (FunctionTool)
  Output Key: user_profile
  DB Table:   user_profiles

  How it works:
  - System prompt instructs Gemini to be a warm, professional assistant
  - Asks 1-2 questions at a time (not a form)
  - Can handle Hinglish and regional language input
  - Infers from context (e.g. "we make pickles" → sector: food_processing)
  - When all 6 fields collected, calls finalize_profile tool
  - Tool validates using Pydantic UserProfile schema
  - Profile persisted to user_profiles table by routes.py

  6 Required Fields:
    1. sector           (agriculture, manufacturing, it_tech, healthcare, ...)
    2. state            (Indian state name)
    3. annual_revenue_inr (INR, 0 for pre-revenue)
    4. entity_type      (startup, msme, private_limited, ...)
    5. team_size        (number of employees)
    6. purpose          (working_capital, capex, r_and_d, technology_upgrade, ...)

  Optional Fields:
    - years_in_operation, is_women_led, is_sc_st_led, has_existing_loans


─── AGENT 2: ResearchAgent (research_agent.py + research_service.py) ───────

  Purpose:    Find 15-20 relevant government schemes via real web scraping
  Model:      Gemini 2.0 Flash (temperature: 0.1)
  Tools:      scrape_and_extract_schemes (FunctionTool), rag_lookup (FunctionTool)
  Output Key: raw_schemes
  DB Table:   raw_schemes
  Agent Type: Module-level Agent instance (not a factory function)

  Source files:
    - research_agent.py     — ADK Agent definition + tool wrappers
    - research_service.py   — 9-step pipeline orchestrator
    - url_discovery.py      — Gemini-powered URL generation + curated portal lists
    - scraper.py            — Multi-strategy web scraper (httpx → Playwright fallback)
    - html_extractor.py     — Gemini HTML-to-JSON extraction + deduplication
    - chroma_indexer.py     — ChromaDB vector indexing + RAG search

  How it works:

    The ADK agent (research_agent.py) defines TWO FunctionTools:

      1. scrape_and_extract_schemes(sector, state, entity_type,
         annual_revenue_inr, team_size, purpose, session_id)
         → Runs the full research_service.run_research_pipeline()
         → Returns {"schemes": [...], "count": N, "status": "ok"|"fallback"}

      2. rag_lookup(query)
         → Searches ChromaDB index for schemes matching a natural-language query
         → Used as fallback when scraping returns status="fallback"
         → Returns {"schemes": [...], "count": N}

    Agent workflow (via ADK instruction):
      1. Extract profile fields from context (passed by IntakeAgent)
      2. Call scrape_and_extract_schemes with all 7 parameters
      3. If status="fallback", also call rag_lookup with
         "{sector} {state} {entity_type}" query
      4. Return combined list as output key "raw_schemes"

    Pipeline service flow (research_service.py — 9 steps):

      STEP 1 — RAG Pre-check:
        - Builds semantic query from profile: "{sector} {entity_type} {state}
          government grant scheme subsidy {purpose}"
        - Searches existing ChromaDB index (rag_search, n_results=15)
        - Adds any matches to the candidate pool

      STEP 2 — URL Discovery (url_discovery.py):
        - Starts with 8 baseline URLs (msme.gov.in, startupindia.gov.in, etc.)
        - Adds sector-specific portals (food_processing → mofpi.gov.in, etc.)
        - Adds state-specific portals (maharashtra → udyog.mahaonline.gov.in, etc.)
        - Calls Gemini API to suggest 8-15 additional targeted URLs
        - Deduplicates, caps at MAX_SCRAPE_URLS (10)

      STEP 3 — Web Scraping (scraper.py):
        - Strategy 1: httpx (async, fast, handles static pages)
          - Rotates User-Agent pool (4 browser fingerprints)
          - Follows redirects, accepts bad TLS (govt sites)
          - 20s timeout, caps HTML at 200K chars
        - Strategy 2: Playwright fallback (headless Chromium)
          - Activates when httpx returns <500 chars (JS shell page)
          - Masks webdriver signals, waits for networkidle
          - 30s timeout
        - Concurrency: 3 URLs in parallel, 0.5-2s jitter between requests

      STEP 4 — HTML Extraction (html_extractor.py):
        - Pre-processes HTML with BeautifulSoup:
          - Strips script, style, nav, footer, header, aside tags
          - Finds main content container by id/class regex
          - Truncates to ~8000 words
        - Sends cleaned text + profile to Gemini with extraction prompt
        - Gemini returns structured JSON array of scheme records:
          {scheme_name, criteria_text, deadline, max_revenue_inr,
           eligible_types, grant_amount, portal_url, source_type}
        - All URLs extracted in parallel (asyncio.gather)

      STEP 5 — Deduplication:
        - Normalizes scheme_name (lowercase, collapsed whitespace)
        - On duplicate, keeps the record with more non-null fields

      STEP 6 — ChromaDB Indexing (chroma_indexer.py):
        - Collection: "govgrant_schemes" (cosine similarity)
        - Document: "Scheme: {name}\nEligibility: {criteria}\nGrant: {amount}"
        - Embedding: Google text-embedding-004 (768 dims)
        - Stable IDs: MD5 of lowercase scheme_name (upsert, no duplicates)
        - Metadata stored: scheme_name, source_url, grant_amount, deadline,
          eligible_types, max_revenue_inr, source_type

      STEP 7 — Final Dedup: Merge RAG results + newly scraped, deduplicate

      STEP 8 — Fallback Gate:
        - If < 5 schemes found after all steps, appends 5 curated schemes:
          CGTMSE, PM Mudra Yojana, Stand Up India, PMEGP, Startup India Seed Fund
        - Deduplicates again after adding fallback

      STEP 9 — Persist:
        - Writes all final schemes to raw_schemes table via SQLModel
        - Uses a dedicated Session(engine) for DB writes
        - Normalizes eligible_types → JSON string, revenue → int or None

    Routes integration (research_service.py helpers):
      - read_profile_from_db(session_id, db) → reads UserProfile → dict
      - run_research(session_id, profile_data, db) → wraps run_research_pipeline()
        with field mapping (type→entity_type, revenue_inr→annual_revenue_inr, etc.)


─── AGENT 3: ValidatorAgent (validator_agent.py + validator_service.py) ────

  Purpose:    Filter ineligible schemes, score remaining, rank top 5
  Model:      Gemini 2.0 Flash (temperature: 0.1)
  Tools:      hard_filter_schemes (FunctionTool)
  Output Key: ranked_schemes
  DB Table:   ranked_schemes

  How it works:

  PHASE 1 — Hard Filter (deterministic, no LLM):
    Removes schemes where the user clearly doesn't qualify:
    ┌─────────────────────┬────────────────────────────────────────┐
    │ Check               │ Rule                                   │
    ├─────────────────────┼────────────────────────────────────────┤
    │ Revenue cap         │ user revenue <= scheme max_revenue_inr │
    │ Entity type         │ user type in scheme's eligible list    │
    │ State               │ user state matches (empty = pan-India) │
    │ Team size           │ user team <= scheme max_team_size      │
    └─────────────────────┴────────────────────────────────────────┘

    Handles both field naming conventions (revenue_inr / annual_revenue_inr)
    Parses JSON-string eligible_types, case-insensitive matching

  PHASE 2 — LLM Scoring (Gemini 2.0 Flash):
    Scores each remaining scheme on 4 dimensions:
    ┌─────────────────┬────────┬───────────────────────────────────┐
    │ Dimension       │ Weight │ What it measures                  │
    ├─────────────────┼────────┼───────────────────────────────────┤
    │ Eligibility     │ 0-40   │ Hard criteria match               │
    │ Relevance       │ 0-30   │ Sector/purpose alignment          │
    │ Benefit         │ 0-20   │ Grant value vs business needs     │
    │ Ease            │ 0-10   │ Application complexity            │
    ├─────────────────┼────────┼───────────────────────────────────┤
    │ COMPOSITE       │ 0-100  │ Sum of all 4 dimensions           │
    └─────────────────┴────────┴───────────────────────────────────┘

    Special bonuses:
    - Women-led enterprise: +5 to relevance (if scheme has women preference)
    - SC/ST founder: +5 to relevance (if scheme targets SC/ST)

  PHASE 3 — Ranking:
    - Sort by composite score descending
    - Take top 5
    - Assign rank 1 (best) through 5
    - Calculate urgency_score based on deadline proximity:
        Within 14 days → 1.0
        Within 30 days → 0.8
        Within 60 days → 0.5
        Beyond 60 days → 0.3
    - Persist to ranked_schemes table

  Fallback: If Gemini fails, uses simple descending score (80, 70, 60, 50, 40)


─── AGENT 4: PlannerAgent (planner_agent.py + planner_service.py) ──────────

  Purpose:    Generate complete GrantReport (docs, cards, summary)
  Model:      Gemini 2.0 Flash (temperature: 0.4)
  Tools:      save_grant_report (FunctionTool)
  Output Key: grant_report
  DB Tables:  grant_reports, alerts

  How it works:
  - Reads ranked_schemes from DB (Agent 3 output)
  - Calls Gemini to generate 3 components:

  COMPONENT 1 — Documents Checklist (10-15 items):
    Always includes:
    ┌─ Mandatory ─────────────────────────────────────────────────┐
    │ Aadhaar Card (Promoters)                                    │
    │ PAN Card (Business + Promoters)                             │
    │ Certificate of Incorporation / Registration                 │
    │ GST Registration Certificate                                │
    │ MSME / Udyam Registration                                   │
    │ Bank Account Statements (last 6-12 months)                  │
    │ Income Tax Returns (last 2-3 years)                         │
    │ Business Plan / Project Report                              │
    └─────────────────────────────────────────────────────────────┘
    Plus scheme-specific documents (FSSAI for food, DPIIT for startups, etc.)

  COMPONENT 2 — Action Cards (1 per scheme):
    Each card contains:
    - scheme_name: Official name
    - portal_url: Direct application link
    - deadline: ISO date or "Rolling"
    - steps: 5-7 ordered application steps
    - estimated_days: Realistic working days estimate
    - tips: 2-3 insider tips for that scheme

  COMPONENT 3 — Cover Summary (150 words):
    - First person ("We/Our business...")
    - Introduces business (name, sector, state, entity type)
    - Highlights strengths (team size, revenue, growth)
    - States funding purpose and alignment with government objectives
    - Ends with confident request for consideration
    - Copy-to-clipboard button on frontend

  Persistence:
    - documents_json and action_cards_json stored as JSON strings
    - cover_summary stored as plain text
    - All in grant_reports table (unique per session_id)

  Fallback: Curated report with CGTMSE and Startup India Seed Fund cards


================================================================================
6. SSE (Server-Sent Events) STREAMING
================================================================================

The pipeline endpoint (POST /api/pipeline) uses SSE to stream real-time
progress updates to the frontend. The frontend Processing page listens
for these events and updates the agent status cards accordingly.

Four locked event names (DO NOT CHANGE):

    ┌──────────────────┬──────────────────────────────┬────────────┐
    │ Event Name       │ Payload                      │ Agent      │
    ├──────────────────┼──────────────────────────────┼────────────┤
    │ intake_done      │ UserProfile JSON             │ Agent 1    │
    │ research_done    │ Scheme[] array               │ Agent 2    │
    │ validation_done  │ RankedScheme[] top 5         │ Agent 3    │
    │ report_ready     │ GrantReport JSON             │ Agent 4    │
    └──────────────────┴──────────────────────────────┴────────────┘

SSE format:
    event: research_done
    data: [{"scheme_name": "PM FME Scheme", ...}]

    event: validation_done
    data: [{"scheme_name": "PM FME Scheme", "match_score": 92, ...}]

10. HOW TO RUN
================================================================================

Prerequisites:
    - Python 3.11+
    - Node.js 18+
    - GOOGLE_API_KEY in govgrant-backend/.env

Terminal 1 — Backend:
    cd govgrant-backend
    pip install -r requirements.txt
    python -m uvicorn main:app --reload --port 8000

Terminal 2 — Frontend:
    cd govgrant-frontend
    npm install
    npm run dev

Open: http://localhost:3000
